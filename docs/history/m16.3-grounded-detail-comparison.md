exact reference admission, predecessor selection, restart continuity and response

result identities. M16.2 still inserts complete authoritative claims and keeps

`dialogue_evidence.py` adds an optional ephemeral `DetailRequest`, bounded
publication readers and two thin result-shape adapters. `sessions.evidence`
forwards that optional request. `scientific_dialogue.py` includes available
reviewed detail in the same claim context, checks comparison eligibility, and

## E–F. Integrity and bounds

```python
from agent.application import DetailRequest
view = app.sessions.evidence(
    session_id, revision_id, output_name,
    detail=DetailRequest("annotation_rationale", subject="3", limit=8),
)
```

The exact accepted result supplies `manifest_path` and `manifest_sha256`.
Only contract-defined sidecar names are read from that pinned manifest. Manifest
contract/type/version and supported profile are checked. When accepted authority
is present, its publication binding and exact sidecar closure entry must also
match. Each read checks canonical absolute regular-file paths, exact digest and
sidecar byte size. Publications outside the application workspace are supported
through these exact accepted bindings. No directory search or guessed path occurs.

Each JSON/compressed artifact is capped at 8 MiB before parsing. Decoded histogram
text is capped at 64 KiB. Requests select a section, an exact optional subject,
an optional exact annotation candidate and 1–32 records (default 8). Whole fields
are capped at 16 KiB, evidence views at 64 KiB, provider context at 32 KiB, and
claims at 64 with a per-operand allocation. Oversized fields have explicit
`omitted` status; record omissions and candidate selection are explicit. Excessive
artifact/context sizes fail closed. No selected record or marker list is silently
sliced. Record order is publication order, never a ranking.

Detailed facts carry sidecar name, digest and exact JSON pointer or text line.
Returned claims additionally retain revision, output locator, accepted run-result
and evidence identities. Evidence is reloaded after generation, rejecting changed
consumed claims. This checks accepted publication integrity, not fresh scientific
correctness or upstream re-verification. Trusted-local filesystem race limitations
remain; this is not a hostile-filesystem sandbox.

The direct detail API returns no facts on missing/corrupt/unsupported detail.
Dialogue can still discuss valid compact evidence while explicitly reporting
unavailable detail; unavailable detail supplies no claim and cannot become rationale.

## G. Annotation rationale

The adapter reads existing `primary/groups.json`, `candidate_evidence.json` and
`signature_coverage.json`. It exposes assignment/status, recorded reason, existing
candidate score, signed matched-marker lists, unobserved marker genes and signature
coverage. It neither scores candidates nor discovers markers. In dialogue the
existing accepted assignment selects its exact candidate; other candidates are
explicitly unrequested. The direct API can request all candidates within the bound
or another exact candidate. No score-based ranking or winner recomputation occurs.

Four scripted turns over the preserved real owner-produced annotation result
passed: cluster 3 rationale, cluster 7 follow-up, existing supporting-evidence
comparison and a limitation question. Owner annotation, scoring, matrix loading,
verification, execution and presentation entry points were guarded against calls.
The evidence was read in place; only isolated interaction copies were written.
This is accepted-evidence access, not renewed biological qualification.

## I–J. Comparisons

Two operands retain exact revision, run, step, output, subject, field/value and
accepted evidence attribution. Tool, result contract and recovery identity must
match. Within an exact accepted result, existing subject evidence can be compared;
matching cluster numbers in distinct results never establishes correspondence.

The initial cross-result rule admits selection results only when their exact QC
identity/population, selection contract/method, calling semantics, qualification
and observed-barcode count agree. Present profile/resource/reference identities
must agree too. Existing thresholds and selected/rejected counts can differ.
The pinned selection contract/recovery identity supplies the reviewed method;
no field-name-only compatibility is used. Other cross-result capabilities fail
closed until a reviewed scope rule is supplied, including evaluation, matrix and
QC cross-result comparisons. This intentionally tightens M16.2's broad guard.

Only compatible field pairs are offered. Candidate records pair by exact candidate
identity, never their list offset. A `comparison` part references one offered pair;
the Agent inserts both complete operands and their exact `equal`/`different`
relationship. Existing individual claim parts remain supported, but a supported
comparison must include a compatible pair. No difference arithmetic, significance,
effect size, inferred correspondence, ranking or new statistic is produced.

No ranking criterion is offered. The interpreter is instructed to clarify
“biggest difference” without an explicit dimension. Structured comparison records
cannot express a ranking. As in M16.2, arbitrary explanatory prose does not have a
complete deterministic entailment proof; this is not a new claim of semantic
validation for every model-authored sentence.

## K–M. Multi-turn boundaries and no-work accounting

The ordinary predecessor/subject mechanism supports:

1. “Why was cluster 3 annotated this way?” — exact published assignment/rationale.
2. “What about cluster 7?” — reload the other exact subject.
3. “How do their supporting markers differ?” — bound existing operand records.
4. “Does that prove distinct cell types?” — insufficient evidence and reviewed limitations.

Requests for new markers, reannotation or significance remain outside this layer;
existing execution routing or unsupported/clarification handles them. No implicit
execution was added. Interpretation/detail/comparison perform zero owner execution,
owner reconstruction, report rebuilding, statistical analysis or annotation inference.
Tests cover in-process restart continuity; existing fresh-process M16 tests remain
in the focused regression. Durable records still contain references, not generated
scientific facts or prose.

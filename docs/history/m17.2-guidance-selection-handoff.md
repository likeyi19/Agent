## Ownership and reuse

The new `guidance_selection` module fills one application ownership gap: resolve
an explicit selection of an existing M17.1 reference into normal planning intent
and authorized context. It constructs no steps, DAG, tool arguments, prerequisites
or scientific authority. No new request model or persistence store is introduced.

| Owner | Responsibility |
| --- | --- |
| `turn_decisions.ExecuteCandidate` / `interpret` | Semantic candidate selection and literal current-turn command evidence |
| M17.1 `Interaction.guidance_candidates` | Existing immutable candidate, origin/objective turn, base revision, capability and evidence identities |
| `scientific_dialogue.capture` / `public` | Existing captured discussion chain and ambiguity; bounded execution-candidate inventory |
| `guidance_selection` | Exact lookup, applicability checks, command admission, authorized context and request text |
| Existing `AnalysisSession` / `FileSessionStore` | Durable immutable interaction metadata; the existing capture validator now checks selected references on load |
| Existing `dialogue_execution.execute` / `_AdmittedPlanner` | Ordinary AgentRequest, delegated planning, actual-plan output selection and SessionTurn admission |
| Existing M15.3 `binding_for_locator`, `validate_binding`, `ActivePlanningContext` | Exact historical publication identities and scientific authority checks |
| Existing scoped Planner, semantic compiler, executor/preflight | Workflow/source choices, legal bindings, argument/resource validation and execution |

The semantic-minimum decision is `{kind: execute_candidate, candidate, evidence}`.
Agent derives capability, revision, request identity and canonical execution branch
from the admitted reference. No model-authored base, operation, delta or capability
assertions duplicate those facts. The new decision type is exported alongside the
existing interaction types. Existing wire branches and canonical decisions retain
their behavior.

## Explicit selection and stable references

The interpreter sees at most the original M17.1 option set, with stable IDs,
canonical original ordinals, registered capabilities, captured subjects and the
original user objective. It semantically resolves “Option 1” or a named option;
Agent performs an exact lookup. There is no phrase-to-tool table or deterministic
biological inference. Literal command evidence must be a complete current-turn
command clause; the existing rejection of conditional/negated commands is reused.
Interest, agreement or a rationale question alone cannot admit this branch.

The inventory follows the captured discussion predecessor chain. A rationale
follow-up retaining one candidate still resolves execution ordinals against the
original option set. Unrelated scientific discussion can retain the same chain.
Multiple conversation heads or pending competing discussion supply no implicit
candidate inventory. Explicit predecessor selection uses the existing session API.
Restart/replay uses persisted references, never regenerated rationale or arrival
order. Execution replay recovers the existing turn and does not plan again.

Unknown and wrong-session references fail closed. References captured against a
different active revision are rejected, including when explicitly offered via an
old predecessor. There is no silent rebase. Returning through normal navigation
to the exact captured revision can make it eligible again; current generation is
captured anew and checked before handoff/submission. Catalog identity, registered
capability, exact accepted evidence and supported subject identity are rechecked.

Natural-language ambiguity and compatibility of refinements remain semantic
interpretation responsibilities. The interpreter must clarify unresolved “other”
references or conflicting subject/revision changes. Deterministic checks validate
identities and contracts; they do not claim to prove arbitrary prose entailment.
Scripted tests establish software behavior, not live-model interpretation quality.

## Request, bindings and execution

The ordinary `AgentRequest` combines the original user objective, selected
capability, exact subject-to-context-handle correspondence, verbatim current user
request and explicit caller `execution_inputs`. No rationale becomes a fact.
Refinements such as a new comparison reach the existing Planner without editing
the original candidate. Captured subject identity stays fixed; unavailable or
contradictory requests must clarify or fail normal planning/contract validation.

Only the selected candidate's captured evidence is considered for context; there
is no scan for convenient historical inputs or implicit retention of all outputs.
Each locator must independently produce a reusable M15.3 binding and pass integrity
validation. Readability alone is insufficient. This initial bridge conservatively
rejects the handoff if any selected evidence lacks reusable authority; it does not
silently drop that evidence or replace it with caller data. Empty evidence sets
can use explicit inputs on the already-required accepted session revision.
Bindings are deduplicated and exposed as ordinary `ctx.N` handles. Private run IDs,
hashes and authority payloads are not added to provider planning context.

`dialogue_execution.execute` enters the existing context manager and delegates
through `_AdmittedPlanner` to the configured Planner. Candidate capability is an
intent constraint checked against the resulting plan, not a constructed tool call.
Normal output selection, compiler, preflight and execution admission remain in
force. Evidence/context are checked again before linking the turn, with an atomic
revision/generation check at submission. Subsequent execution/recovery uses the
existing historical integrity and stale-activation machinery.

Unknown references, stale state, removed capability/catalog changes, missing
subjects, corrupt evidence and unauthorized bindings reject before planning.
Planner/compiler failures cannot form an accepted execution. Preflight failures
cannot run science. No candidate is repaired, substituted or silently rebased.
Read-only M17.1/M16 questions continue through their existing paths.

## Boundaries

readiness/prerequisite engine, ranking, autonomous execution, guidance authority
or store, synthesis engine, provider branch, schema relaxation or repair logic.
Scientific contracts, Registry, owners, EpiZoo and provider transports are unchanged.

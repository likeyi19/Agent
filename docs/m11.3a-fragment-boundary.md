# M11.3a — Producer-neutral fragment boundary

M11.3a establishes `agent.scatac-fragments`, schema 2, contract
`scatac-fragments.v2`, plus a common freshly verified v1/v2 streaming view.
It adds no registered scientific tool. The registry remains at 13 tools.

M11.2 FASTQ execution still publishes v1 with its exact Chromap support,
whitelist, index, verification, recovery, planning and reporting contracts.
Existing v1 artifacts and persisted results are neither migrated nor rewritten.
The existing production modules are unchanged.

M11.3b external-fragment adoption and M11.3c qualified BAM production remain
future execution work. Their producer qualification, source interpretation,
transformation and durable publication are not implemented here. CRAM and SAM
remain unsupported. M11.4 cell selection/QC, TSS/FRiP, cCRE overlap, matrices,
H5AD construction and model inference remain unimplemented in this path.

## Contract and physical representation

The strict JSON domain is in `src/agent/tools/data/scatac_fragments_v2.py`.
All nested shapes are closed. Version fields reject booleans; missing/unknown
fields, duplicate JSON keys, nonfinite values and unsupported discriminators
fail. JSON is UTF-8 and bounded to 8 MiB. Canonical serialization sorts keys,
uses compact separators and no trailing newline. Manifest loading requires the
expected SHA-256 of the actual bytes and reads no scientific resource contents.

The manifest binds one exact M11.1 reference-manifest path/hash, portable
reference identity, species/assembly and ordered contig identity. Only human/hg38
and mouse/mm10 are accepted. It adds no Chromap index requirement. Reference
reinspection checks the existing FASTA/FAI/cCRE/optional annotation identities;
FAI is the ordered dictionary authority. These checks do not authenticate the
biological assembly or independently establish FASTA/FAI sequence correspondence.
No cCRE overlap or matrix operation occurs.

Libraries are sorted by unique explicit namespace, using the existing
`[A-Za-z0-9][A-Za-z0-9_.-]{0,127}` syntax. At most 4096 libraries and 4096 total
source bindings are permitted. Namespace determines each artifact directory:

```text
libraries/<namespace>/fragments.tsv.gz
libraries/<namespace>/fragments.tsv.gz.tbi
```

Each library declares one uniform strand mode:

| Mode | Canonical data row | Common reader state |
| --- | --- | --- |
| `absent` | `contig TAB start TAB end TAB barcode TAB support LF` | `None` |
| `present` | Same five fields, then `TAB strand LF` | Exact `+`, `-` or `.` |

Present strand requires an explicit bounded definition. `.` preserves a supplied
unknown/unassigned strand; it is distinct from the absence of strand information.
There is no inferred strand or silent sixth-column removal. Mixed row widths,
headers, blank rows, CR/NUL and incomplete final lines are invalid.

Coordinates are 0-based half-open with `0 <= start < end <= exact_FAI_length`.
Numbers use canonical unsigned decimal spelling. No aliases, clipping or repair
are allowed. The library-local key is `(contig, start, end, barcode, strand-state)`;
support is not part of the key. Repeated complete keys fail, including when
support differs. Opposite strands remain distinct records.

Ordering is FAI rank, numeric start, numeric end, ASCII barcode, then ASCII strand
(`+`, `-`, `.`) when present. An absent-strand library has a constant absent state.
The canonical stream SHA-256 covers every exact UTF-8 row and its final LF.

Barcode identifiers are opaque ASCII graphical text (bytes 33 through 126),
1..256 characters. This permits suffixes and punctuation while excluding empty
identifiers, whitespace, control characters and non-ASCII ambiguity. No trimming,
case conversion, normalization, suffix removal, whitelist check or correction
occurs. Cell identity is `(namespace, barcode_identifier)`. Distinct identifiers
observed in fragments are not called or QC-passed cells.

Support is an exact positive integer through `2**64 - 1`. Counts and support
aggregates are checked through `2**128 - 1`, including across libraries; no float
conversion or narrowing occurs. Summary consistency includes record count,
distinct identifier count, sum and maximum support. The bound on summed values
does not assert scientific comparability of different libraries' support units.

Canonical files are BGZF with a terminal EOF marker and BED-preset TBI indexes.
The entire FAI dictionary must fit the existing `2**29` TBI coordinate limit;
there is no CSI fallback. BGZF/TBI full-byte hashes and sizes are recorded.
V2 defines canonical logical bytes, not one mandatory compressor build/level
or cross-build physical-byte reproducibility. Future producers must record their
own execution/packaging profile.

The logical fragments identity hashes `agent.scatac-fragments.v2` plus NUL plus
canonical JSON, excluding its own identity, reference locator, provenance-resource
locators and physical BGZF/TBI entries. It retains exact upstream manifest/profile/
source identities and all scientific declarations, library identities and stream
summaries. Source bindings sort by role, content hash and locator; locator ties
with identical content do not change the locator-free payload. Exact upstream
manifest hashes can themselves be location-sensitive. The separate manifest hash
protects all loaded bytes, including physical artifact identities and locators.

## Producer provenance and qualification boundary

Every library has a closed `fragment-producer-provenance.v1` record. The supported
structural discriminators are `external_fragment_adoption`,
`bam_fragment_production`, and reserved `fastq_fragment_production`; they describe
intended provenance kinds, not executable capabilities or qualified v2 backends.

Required fields are:

- A named profile identity and external profile resource path/SHA-256/size.
- Explicit resource bindings: `external_fragments`, or `bam` plus exactly one
  `intake_manifest` and `library_context`, or `fastq` plus exactly one of each
  manifest/context. Repeated source locators are rejected.
- A producer-record resource identity, required for the reserved FASTQ kind to
  retain rich producer-specific lineage; optional with explicit `null` for the
  other kinds. Its schema/interpretation requires producer-specific verification.
- Support unit (`read_pairs`, `paired_mappings`, or `source_records`) and an exact
  bounded definition describing the counted population under the bound profile.
- Separate Tn5, deduplication, MAPQ-filtering and barcode-correction claims, each
  either `declared` with bounded text or `unspecified` with `null` description.
- Source selection: `all_source_records`, `producer_subset`, or `unspecified`.
- Fixed `producer-specific-verifier-required.v1` verification requirement.

These are closed records and resource/profile identities, not arbitrary inline
JSON or executable parameters. Profile documents and producer records are opaque
to the generic verifier: it checks their bytes, not their interpretation. No
Sinto, SnapATAC2 or other v2 producer is allowlisted or qualified in M11.3a.
A profile name/hash, declared description or producer-record file cannot make
historical processing verified. Unknown processing remains explicitly unknown.

A future producer-specific verifier must validate the reviewed profile, actual
source contracts and the consistency/meaning of these claims before downstream
scientific eligibility is established. In particular, generic content verification
does not prove that intervals were Tn5-adjusted, that duplicate support has a
particular biological meaning, or that source filtering preserved the population
needed for cell calling. Consumers must not treat this data-layer view as that
missing producer qualification or as a persisted execution attestation.

### Future FASTQ convergence (acceptance-audit correction)

The initial M11.3a discriminator allowed only external adoption and BAM production.
That was a structural limitation under the subsequently accepted requirement for
new FASTQ runs eventually to converge on v2. The narrow correction reserves an
explicit FASTQ kind with closed source roles and a required bound producer record.
No FASTQ production, migration, or v2 producer qualification is added.

The profile and producer-record resource slots can retain a reviewed closed,
versioned FASTQ/Chromap record without flattening its fields into generic prose:

| Existing qualified FASTQ information | Future v2 representation |
| --- | --- |
| Backend policy, executable/build/qualification hashes, mapping/packaging policy | Bound profile and producer-specific record |
| Reference-index identity/hash and exact intake/context/reference lineage | Producer record plus direct reference/intake/context identities |
| Whitelist, correction policy, source selection, library/group/role bindings | Producer record and its exact context binding; explicit namespace |
| Decoded-role hashes, normalized-name/order identity, scan counts | Producer record, distinct from encoded FASTQ resource hashes |
| Chromap Tn5 policy and exact paired-mapping support definition | Explicit processing/support metadata plus producer record |
| Canonical stream, BGZF/TBI hashes and exact summaries | Unchanged common v2 artifact fields |

A synthetic representability test binds an entire accepted closed v1 manifest
as the producer-record resource, preserving its exact bytes and every field while
iterating through v2. This is a witness of storage capacity, not a migration API
or a requirement that future new FASTQ runs first publish v1. The future producer
must construct a reviewed record directly and enforce its schema, mandatory
scientific fields, cross-bindings and profile eligibility in its own verifier.
Generic verification hashes the record itself; it does not recursively verify
resources merely mentioned inside it or interpret its claims.

Future FASTQ publication must establish exact encoded source hashes required by
v2; these cannot be invented from v1's bounded intake observations or decoded
stream hashes. The existing producer's full scan provides an integration point,
but this additional identity work and its IO cost are deferred.

M11.3d/joint closeout is the default candidate for FASTQ convergence, after v2 has
been exercised by external-fragment and BAM producers. It should add a new v2
publication path, rich provenance construction, producer-specific verification,
and backward-compatible ToolSpec/result/recovery/evidence/report evolution.
The core coordinates, keys, support representation and streaming interface need
no redesign or FASTQ-specific downstream iteration branch. M11.4/M11.5 remain
future consumers; scientifically justified producer-aware interpretation is separate.
Historical v1 reading, verification and persisted-run compatibility remain permanent.

## Independent verification and publication

`verify_fragments_v2()` independently validates canonical records without using
the downstream reader. It reuses only the source-neutral BGZF block decoder and
tabix query helper from the existing v1 verifier, and existing packaging-runtime
qualification and reference helpers. It calls no FASTQ preflight, Chromap/index
gate, correction, alignment, deduplication, import or source-format parser.

Fresh checks include strict manifest identity; reference/source/profile/producer-
record byte identities; complete BGZF CRC/ISIZE/EOF decoding; row syntax and
width; coordinates, identifiers and strand; ordering/key uniqueness; full record
digest/count/sum/max/distinct identifiers; and TBI contig inventory, complete
represented-contig queries and deterministic narrow overlap queries.

Resource/manifest/artifact snapshots span verification. Paths are absolute,
normalized, regular and resolve without symlink components. Checks assume a
trusted local filesystem and do not promise hostile race/rollback protection.
Memory holds the manifest, reference dictionary and observed distinct barcode
identifiers, but never a complete fragment-row array. M11.1 reference reinspection
also retains a set proportional to cCRE feature identities for duplicate detection;
this precedes fragment streaming and is separate from the reader's memory bound.

The immutable verification result retains exact original manifest bytes/hash and
separately reports `artifact_content=verified`, `bound_resource_identities=verified`,
`producer_history=not_verified` and `producer_profile_qualification=not_established`.
This establishes resource identity, not source authenticity, biological assembly,
barcode truth or independent reconstruction of producer history.

`publish_fragments_manifest_v2()` verifies already-existing canonical artifacts,
writes/fsyncs a sibling temporary JSON file, and publishes it by atomic no-clobber
link followed by directory fsync. Existing destinations conflict. It generates
no BGZF or index and performs no adoption. Future producers own private bundle
staging and atomic directory publication/recovery. As with M11.1 publication, a
directory-fsync failure after linking can leave a complete manifest; no automatic
overwrite/recovery is implied.

## Common verified interface

```python
from agent.tools.data.scatac_fragment_reader import open_verified_fragments
from agent.tools.data.scatac_fragments_v2_verifier import FragmentVerificationRuntime

view = open_verified_fragments(
    manifest_path,
    expected_sha256=manifest_sha256,
    runtime=FragmentVerificationRuntime(),
)
for library in view.libraries:
    support_definition = library.support_meaning
    for fragment in view.iter_fragments(library.namespace):
        cell_identity = fragment.cell_identity  # (namespace, exact identifier)
        # contig, start, end, barcode_identifier, integer support, strand
```

The packaging runtime uses the existing qualified bgzip/tabix/sort identities,
with no aligner field or environment discovery. Opening invokes the exact selected
artifact verifier; v1 uses the unchanged M11.2 verifier and therefore retains its
existing source/resource requirements. Version dispatch uses the explicit artifact
discriminator, never filenames or trial/fallback parsing.
Dispatch preserves v1's accepted JSON byte encodings (including UTF-16 and UTF-8
BOM) and exact original bytes; the selected v2 verifier still requires strict
UTF-8. The acceptance audit reproduced and fixed premature rejection of these
valid v1 encodings by the initial common reader. Duplicate-key/nonfinite/size/hash
checks still apply before dispatch; version-specific validation remains mandatory.

V1 retains its original manifest and qualified Chromap policy; its bound-resource
coverage is labeled `legacy_v1_defined_checks`, not upgraded to full raw-file
hashing. Its historical alignment/correction/deduplication is still not rerun.
Neither v1 nor v2 gets a fabricated alternate-version manifest. Metadata access
returns copies; records/libraries/views are frozen objects.

Iteration selects an explicit namespace, preserves canonical order, and yields
one record at a time. Snapshot checks run before/after reading, including explicit
early close; complete exhaustion additionally checks the stream digest. The
50,000-record test verifies lazy decoding and less than 2 MiB peak traced reader
allocation after opening. Up-front verification's distinct-identifier set is
separate from streaming-reader memory. No filtering or scientific transformation
occurs in this interface.

## Acceptance

Tests use tiny synthetic resources and the existing `agent` environment with
`PYTHONDONTWRITEBYTECODE=1`, `PYTHONPATH=src`, and Numba/Matplotlib caches under
`/tmp`. Ordinary tests fake only tabix process boundaries. Two local real-tabix
tests exercise both column layouts and rehashed invalid indexes; they require
only the existing qualified packaging runtime, not BAM tools or Chromap.

Focused command: `python -m pytest -q tests/tools/data/test_scatac_fragments_v2.py
tests/chromap/test_fragment_reader.py`.

Direct regression: `python -m pytest -q tests/tools/data/test_scatac_reference.py
tests/tools/data/test_scatac_library_context.py tests/chromap
tests/tools/data/test_scatac_fragments_v2.py`.

Full lightweight regression: `python -m pytest -q`, without exclusions or enabled
biological/model/backend qualification gates. Counts overlap and are not additive.

## Reviewed source profile

The only accepted explicit profile is **`10x-atac-fragments.v1`**, a versioned
logical source-semantics contract covering Cell Ranger ATAC/ARC fragment exports.
It is not automatic software/version detection. A filename, extension, header,
barcode, column count or nearby index never selects the producer or reference.
Additional profiles require reviewed code and verification; there is no arbitrary
parser or permissive generic-fragments profile.

The current official [Cell Ranger ATAC fragment documentation](https://www.10xgenomics.com/support/software/cell-ranger-atac/latest/analysis/outputs/fragments-file)
and [Cell Ranger ARC fragment documentation](https://www.10xgenomics.com/support/software/cell-ranger-arc/latest/analysis/outputs/fragments-file)
(both showing v2.2 at review) specify already Tn5-adjusted, zero-based, end-exclusive
intervals, corrected barcode identifiers, read-pair support including the
representative and duplicates, and BGZF with a tabix BED index. Their strand
column describes adapter origin: R1 is `+`, R2 is `-`.

This profile admits the historical five-column layout and the six-column layout.
Five-column data publishes strand mode `absent`; common iteration returns
`None`, never a synthesized dot. Six-column data preserves `+`, `-` or supplied
`.` (unknown) exactly. Dot is the explicitly admitted v2 unknown state, not a
claim that every Cell Ranger version emitted it. Mixed layouts fail. Strand
participates in the complete canonical key, so opposite strands remain distinct.

Support means the total read pairs associated with the supplied unique fragment,
including representative and duplicate pairs under the caller-declared profile.
It is parsed without floating conversion as positive uint64; checked aggregates
use uint128. Values above 255 are preserved. This support definition is specific
to this profile and is not generalized to other producers.

## Physical source, headers and identity

Plain text, ordinary gzip and BGZF are detected from bytes and validated through
complete sequential decoding. Suffixes have no authority. Records must be UTF-8,
TAB separated and LF terminated, with canonical unsigned decimal integers.
CR, NUL, missing terminal LF, blank records, signed/fractional/leading-zero
integers and malformed compression fail closed.

Leading `#` header records are opaque provenance, with limits of 65,536 bytes per
line including LF, 1,024 header records and 1 MiB total header bytes. Comments
after data fail. Headers are hashed exactly, never copied into report facts;
no free-form assembly/sample metadata is parsed or promoted to authority.

The closed `agent.external-fragment-adoption` record, schema 1, contract
`external-fragment-adoption.v1`, binds:

- Exact absolute regular-file source path, complete encoded SHA-256 and size;
  validated physical encoding; complete decoded, data-only and header SHA-256;
  header byte/record counts; actual column layout, record count and support sum.
- Exact published profile bytes/hash and optional explicitly supplied source
  index path/hash/size.
- Exact reference manifest path/hash, reference identity, ordered-contig digest,
  species/assembly, explicit namespace and declared source selection.
- Fixed transformation policy and all canonical summaries: stream digest, record
  count, support sum, maximum support and distinct observed barcode count.

The record is bounded to 32 KiB and rejects unknown/missing fields, duplicate
JSON keys and nonfinite numbers. The closed profile resource records the policy,
limits and semantic references. Both resources are bound through v2's existing
`external_fragment_adoption` provenance variant. No raw-intake or library-context
manifest is manufactured, and no Chromap/FASTQ/BAM execution is asserted.

Source index path and SHA must be supplied together or both absent; no adjacent
`.tbi` is discovered. An index is accepted only for BGZF. Verification checks its
exact bytes, compressed integrity and BED tabix preset, plus reference listing,
full per-contig queries and narrow interval queries against completely scanned
source records. Temporary links expose exactly the supplied source/index pair
to tabix. Stale, corrupt or mismatched indexes fail. This establishes functional
compatibility with the bound source, not the index's historical creator. Without
a source index, sequential adoption remains valid and output receives a newly
generated verified TBI; no original-index claim is made.

## Reference, namespace and selection

An explicit accepted `ScATACReferenceBundle` and expected manifest SHA are
required. Reference resources are freshly checked. Production pairs remain
human/hg38 and mouse/mm10. Every fragment contig must occur in the exact FAI and
its coordinates must fit that contig. A subset of FAI contigs is allowed.
FAI order controls canonical sorting. No aliases, prefix repair, clipping,
liftOver, assembly inference or conversion occur. The existing TBI coordinate
ceiling remains enforced.

One source file creates one library with one explicit processing namespace.
Identity is `(namespace, barcode_identifier)`. Safe bounded v2 barcode tokens
are preserved exactly, including case and suffixes such as `-1` and `-2`.
No whitelist, correction, suffix splitting or library reconstruction occurs.
Observed identifiers are not called cells.

`source_selection` accepts `full_export`, `subset_export` or default `unknown`,
mapping to v2's `all_source_records`, `producer_subset` or `unspecified`.
This is caller-declared historical coverage, never inferred from data. All rows
of every admitted source are conserved regardless of this declaration.

## Canonicalization and independent verification

The exact transformation policy is
`validate-sort-serialize-bgzf-tbi;no-biological-transformation.v1`.
After complete validation, managed external sorting orders records by reference
rank, start, end, exact barcode and optional strand. Duplicate complete keys
fail; support is never summed and no first/last row wins. Serialization,
compression and indexing preserve coordinates, support and strand. There is
no second Tn5 shift, realignment, deduplication, MAPQ filter or biological merge.

Production and producer-specific verification use separate record parsers.
Verification fully rehashes/redecodes/reparses the source and independently
reconstructs its canonical stream through managed external sorting. Comparison
includes exact stream digest and all summaries, not just aggregate counts.
It composes the unchanged generic v2 verifier for output BGZF/TBI identities,
integrity, canonical ordering, reference bounds, exact stream summaries and
functional queries. Profile, adoption-record, source-index and caller bindings
are checked independently. Snapshots before/after IO detect mutation within the
existing trusted-local-filesystem model; this is not hostile-filesystem security.

The verification result distinguishes source content verified, canonicalization
conservation verified, and producer history declared/not reconstructed. It does
not reconstruct upstream alignment, MAPQ filtering, Tn5 processing, duplicate
determination, barcode correction or cell calling. The generic v2 reader retains
its generic guarantees; it does not silently gain producer-history verification.

Packaging reuses qualified `/usr/bin/sort`, `/usr/bin/bgzip` and
`/usr/bin/tabix` machinery without requiring Chromap, its index/environment,
samtools, Sinto, SnapATAC2, GPU or a foundation model. Sort uses a 64 MiB working
buffer, one thread and the C locale. No full fragment dataset is retained in
memory, but existing verification tracks distinct barcodes and reference resources;
memory is not constant in barcode cardinality. Fresh verification rereads and
sorts the source, so its cost scales with source size and requires scratch disk.

## Publication, recovery and Application reporting

Dedicated immutable recovery policy: `import-scatac-fragments-external-v1`.
Exact normalized arguments, source/reference hashes, output destination, policy
and durable run/plan/step/tool identity determine one publication token/path.
A private locked staging envelope contains the fragments and a closed receipt.
Production and independent verification finish in staging. Only the two locally
produced profile/adoption resource locators are rebased to the final destination;
their bytes/hashes and logical fragment identity stay fixed. The final manifest
hash enters the receipt. Files/directories are fsynced, the envelope is atomically
renamed, and published output is freshly verified before success is returned.

Publication-before-checkpoint recovery targets only that exact destination and
receipt, then freshly verifies source/adoption/output before reconstructing a
result. Missing/corrupt/wrong receipts or changed source fail closed. No directory
scan, arbitrary reuse, overwrite or automatic scientific retry is introduced.
Failed private attempts are removed; a published artifact survives a later
checkpoint/cancellation boundary and can be recovered only with the exact identity.
Existing runtime cancellation semantics remain authoritative.

Evidence and deterministic figureless reports use an explicit closed authority
for this tool. They freshly verify publication and project bounded route/profile,
encoding, reference, namespace, selection, record/support/barcode summaries,
strand, transformation and separate verification/history facts. Artifacts include
manifest, canonical BGZF/TBI, profile, adoption record and source, plus supplied
index when present. The optional index evidence field `adoption.source_index`
is reached through the bound adoption record, not a new v2 root field.
Raw headers, rows and barcode values are not report facts. Application PLAN_ONLY,
EXECUTE, planner-free resume, receipt recovery and fresh-evidence corruption
failures are exercised. No new runtime or application execution engine was added.

# M11.6a — Production resource specification and operator workflow

Base: clean `main`, `88dd7adeb04a8ee72422be4b84ea4577417478a2`
(`Complete Milestone 11.5c Agent integration`). This is a specification freeze
for review, not a production-resource qualification attestation. No biological
payload, production bundle or index is created here.

M11.6a specifies operator decisions and procedures; M11.6b obtains authoritative
parent/QC resources and attestation; M11.6c provisions full-reference Chromap
indexes and hands off the runtime. M11.7 will assess real-data operational
execution. M11.8 retains biological validation/acceptance, including the raw
routes historically assigned there in [AGENTS.md](../AGENTS.md).

### Product comparison and compatibility gate

Both official pages distinguish CHR, PRI (chromosomes plus scaffolds), ALL
(including patches/alternate loci), and basic subsets. CHR comprehensive is
selected because the approved QC scope is canonical nuclear chromosomes and
the frozen science uses all eligible transcript TSSs, not only basic transcripts.
PRI/ALL add non-QC annotation and introduce additional contig compatibility
requirements without extending the approved QC scope. They are not fallback
products. No filtering of the downloaded CHR file is authorized.

Bounded local FAI inspection reproduced the accepted 455-contig human and
66-contig mouse dictionaries and their exact hashes below. Human entries for
chromosomes 1–22, X, Y and M, and mouse entries for 1–19, X, Y and M are present.
This is a structural comparison with the selected CHR coverage, not proof of
annotation coordinate compatibility or sequence authenticity. Every transcript
contig and end coordinate must pass exact parent checks during M11.6b, including
records later excluded from TSS selection. No aliases, clipping or row dropping.

The pinned parser is `pysam-0.24.1-gencode-transcript-gtf.v1`, explicitly supplied
as `GTF_PROFILE` (the builder's default is synthetic). It requires plain UTF-8
GTF and its narrow attribute dialect; transcript rows need exact gene/transcript
identities and `gene_type`. `gene_type=protein_coding` determines eligibility;
transcript biotype is not a replacement. The existing parser validates other
feature rows' syntax too. Full payload compatibility is an M11.6b gate, not
claimed from release webpages. Existing row/size/contig/TSS/transcript limits
remain unchanged. Any failure stops provisioning; no parser repair, release
switch, annotation trimming or limit increase is automatic.

### Checksum and acquisition evidence

M11.6b must obtain the release directory's official checksum listing, expected
at `MD5SUMS` beside each archive, and retain the exact listing bytes, source URL,
retrieval time and exact filename entry. Verify the published checksum using its
declared algorithm; also compute archive SHA-256 locally. MD5 is source-download
consistency evidence, not a replacement for SHA-256 identity or source review.

The metadata browser could not retrieve the EBI directory/checksum listings in
M11.6a. No checksum values are asserted or fabricated here. M11.6b must resolve
the official checksum evidence before accepting acquisition; an unavailable or
mismatched entry is a stop condition, not permission to omit it. A different
official listing location must be documented and reviewed, never guessed.

Decompress gzip once, preserving exact decompressed bytes: no newline conversion,
attribute rewriting, filtering or reserialization. Compute SHA-256 and size of
the plain GTF; bind those bytes in the existing QC annotation record. Retain
archive checksum/SHA, plain SHA, and the decompression tool/version/command in
operator evidence. Preserve original source files outside Git. M11.6a freezes
the procedure, not unobserved archive or plain-GTF digest values.

## Complete reviewed contig classification

No final production classification file is created in M11.6a: final authoritative
parent manifests are not yet available. M11.6b will produce `contigs.tsv` per
parent revision, UTF-8/LF, headerless, exactly three tab-separated columns:
`name`, decimal `length`, `classification`. Each row maps directly to existing
`QCContig(name, length, classification)`; this is operator input serialization,
not a new registered scientific artifact. No blank rows, duplicate names or
implicit assignments are allowed.

Every FAI contig appears exactly once, in its original order and length. Only
`primary_nuclear_qc`, `mitochondrial`, and `other` are legal. Use authoritative
assembly component/sequence records to review exact identities. Human canonical
chromosomes 1–22/X/Y and mouse 1–19/X/Y, when present, are primary nuclear QC;
the authoritative mitochondrial sequence is mitochondrial. Every remaining
alternate, patch, unlocalized, unplaced, decoy or other non-primary sequence is
explicitly reviewed and assigned `other`. Missing expected canonical sequences
must be documented in the parent review, never silently ignored.

No chromosome names, prefixes, regexes, lengths, annotation rows or alias guesses
may determine classes automatically. The local FAI name inspection above does
not constitute this biological review. Do not default unmatched rows to `other`.

Acceptance requires exact full FAI row comparison, legal classes, at least one
primary QC contig, and a signed-off review record covering every assignment and
its authoritative basis. Record parent manifest SHA, ordered dictionary SHA,
classification-file SHA and reviewer/date in that record. Supply
`classification_source="sha256-<review-record-sha256>"` to the QC builder.
The record precedes QC construction and must not contain its future QC identity.
Source reinspection checks reproducibility of supplied classifications, not their
biological truth. Valid but incorrect assignments must be rejected in review.

## QC construction and immutable catalog lifecycle

M11.6b calls `build_scatac_qc_reference_bundle` with the exact final parent
path/SHA, selected plain GTF/source/release, explicit `GTF_PROFILE`, reviewed
`QCContig` tuple, classification review identifier and a new output directory.
Independently call `reinspect_scatac_qc_reference_bundle_sources`; retain the
canonical TSS/lineage hashes, ordered TSS digest, counts and exclusions. Neither
source declaration nor successful reconstruction is production qualification.

The existing catalog shape remains unchanged:

```json
{
  "artifact_type": "agent.qc-resource-qualification-catalog",
  "schema_version": 1,
  "resources": [
    {
      "resource_identity_sha256": "<exact QC identity>",
      "parent_reference_identity_sha256": "<exact parent identity>",
      "annotation_sha256": "<exact plain GTF SHA-256>",
      "annotation_release": "<49 or M25>",
      "qualification_basis": "sha256-<qualification-review-record-sha256>"
    }
  ]
}
```

This example is illustrative, not a deployable catalog. No fabricated entry is
published in M11.6a. `qualification_basis` identifies immutable operator evidence
covering acquisition, parent authority, classification, parser qualification,
independent reconstruction and explicit production approval of that QC identity.
The `sha256-` prefix plus 64 lowercase hex digits satisfies the existing token
grammar; a colon-separated digest identifier would not be valid in this field.
Runtime validates the token/bindings, not the referenced evidence's truth. The
review record must precede the catalog and not contain its future catalog SHA;
record that SHA separately in deployment evidence.

Use one frozen initial snapshot containing both species after both are reviewed.
The runtime permits 1–16 unique resource identities and at most 64 KiB, with
closed shapes and exactly one matching resource. Serialize once (sorted JSON
keys, compact separators, UTF-8, no trailing newline), hash the exact bytes, and
publish as `catalogs/qc/<sha256>.json`. Canonical formatting is an operator
convention; runtime hashes raw bytes, not normalized JSON.

Never overwrite an accepted catalog. Reformatting or adding an unrelated entry
changes its SHA and creates a new version. Retain exact historical snapshots,
their evidence, and required resources for as long as associated runs are retained
and need fresh verification/recovery. Configure `AGENT_QC_RESOURCE_CATALOG` to
the specific absolute snapshot path, not a mutable `current` file. Historical
verification uses a separately configured process with the original snapshot.

Catalog bytes/basis enter QC publication identity and fresh verification. Drift
between token creation and source binding fails; drift during a run fails;
recovery must bind the exact qualification and cannot scan for similar results.
New catalog bytes can make the old expected publication unavailable. This does
not alter the existing terminal-run stored-result behavior or authorize migration.
Identical catalog bytes may be relocated without changing catalog identity.
QC locator-only rewrites preserve QC logical identity but change manifest SHA;
parent-manifest rewrites change the dependent QC identity too.

Synthetic opt-in cannot promote synthetic TSV resources. GTF fixtures can mimic
the catalog mechanics; operators must reject them as production evidence. The
bundle keeps `source_declared_not_production_qualified` even when an external
catalog approves it. No bundle self-promotion is introduced.

## Filesystem and repository policy

Portable contracts use a deployment root symbol `RESOURCE_ROOT`; it is an
operator notation, not a new Agent environment variable. The selected lab-server
layout is `/home/likeyi/program/agent-resources`. This is a deployment choice for
review, never a runtime default, and no directory is created by M11.6a.

```text
RESOURCE_ROOT/
  sources/{human-hg38,mouse-mm10}/<source-revision>/
  parents/{human-hg38,mouse-mm10}/m116-r1/reference.json
  qc/{human-hg38/gencode-49-chr,mouse-mm10/gencode-M25-chr}/m116-r1/
  build/chromap/<unique-attempt>/<index-directory>/
  indexes/chromap/m116-r1/{human-hg38,mouse-mm10}/
  catalogs/qc/<catalog-sha256>.json
  evidence/{sources,parents,classifications,qc,chromap,deployment}/
  runtimes/chromap/<executable-sha256>/chromap
```

The braces express alternative literal directories, not a discovery mechanism.
An operator deployment record expands every source/evidence revision and absolute
path before parent publication. `m116-r1` is immutable once published; subsequent
changes use an explicitly reviewed new revision, never overwrite. Final resources
cannot reside under `/tmp`. Build space and published indexes must be on the
same filesystem for atomic directory publication. Freeze allocation/capacity
before M11.6c; no build-size or throughput guarantee is claimed.

Git may contain this specification, small reviewed source/checksum evidence,
classification tables/reviews, qualification metadata, and immutable catalog
snapshots. Catalog snapshots have no payload locators. Machine-local deployment
records and executable installations live outside Git; the lab example here is
documentation, not portable schema data. Keep FASTA/FAI, GTF archives/plain files,
TSS, lineage, full cCRE BEDs, source H5ADs, native indexes, logs with payload data,
and biological datasets external. Small dictionary/classification metadata is
allowed; do not copy the underlying biological payload into Git. Review staged
paths/sizes before any later commit.

## Chromap construction and deployment procedure (M11.6c only)

Use the existing patched backend, never stock Chromap:

```text
upstream commit: 5bd17e1f1c50805e76904efd021603cb6a1b6e23
version: 0.3.2-r518
executable SHA-256: 7ba402d0d69d08fedd525a4de83a4dd749670e88d4de507c236b07f03a285649
patch SHA-256: 8d862e77d59213aa19b3fbc5f6014585a4b5f414f3e29143b68513ffd961df33
build record SHA-256: 6bb93fb766aee7e752a71cbe36c305f7c8278b24699c6945fb6491d37ffa974a
backend policy: chromap-atac-agent-support-v1
index policy: chromap-index-k17-w7.v1
```

The complete runtime authority remains [_chromap.py](../src/agent/tools/data/_chromap.py)
and [qualification evidence](../third_party/patches/chromap/QUALIFICATION.md),
including exact linked libraries/platform. Deploy identical qualified executable
bytes at the durable hash-named location and call `identify_backend` there. A
rebuild with different bytes or changed libraries requires separate qualification,
not an edited pin or version-string-only acceptance.

For each exact final parent:

1. Load its expected manifest SHA and reinspect sources; run `verify_fasta_fai`.
2. Call `prepare_chromap_reference_index(reference_manifest_path=...,
   expected_reference_sha256=..., executable=..., backend=...,
   output_dir=...)` in the separate build workspace. Its existing fixed command
   uses `--build-index --ref ... --output ... --kmer 17 --window 7`.
3. Verify the result through `verify_chromap_reference_index`, binding the exact
   parent SHA and backend. Record index manifest SHA, native index SHA/size,
   portable index identity, parent/FASTA/FAI/ordered-contig identities, exact
   argv/profile, executable/toolchain identity, exit outcome and build-log SHA
   in immutable operator evidence. The existing native manifest does not hash
   `build.log`; external evidence must not imply that it does.
4. Perform a separately authorized bounded controlled-input usability check in
   M11.6c. Existing qualification is synthetic, not full-reference biological
   acceptance. Preserve actual native bytes; general byte-deterministic index
   reconstruction is not guaranteed.
5. Under an operator publication lock outside the destination root, require a
   nonexistent destination, fsync the completed files/directory, and rename the
   complete verified index directory onto the same filesystem's published root.
   Fsync affected directories, verify again at the final location, and record
   final locators. Publish only `manifest.json`, `reference.chromap`, and the
   helper's `build.log` within that directory. Keep sibling builder locks/staging
   outside the index root. This is an operator procedure, not a new builder.
6. Activate the revision root only after both child directories pass verification
   and exact runtime lookup. Do not mutate a root used by active runs.

Never call the builder directly inside `AGENT_CHROMAP_INDEX_ROOT`: it leaves a
sibling lock and uses sibling staging. Lookup examines every immediate child
(maximum 4,096), rejects symlink children and malformed/non-directory entries,
and requires exactly one match for reference portable identity, backend and
policy. Subsequent verification checks exact parent manifest and index bytes.
There is no first-match reuse, recursive discovery, fallback or scientific-run
auto-build. Native index content is opaque: binding checks do not independently
prove historical construction from the FASTA; trusted build evidence is required.

## Helper decision and handoff gates

No operator helper is added. Existing builders/validators already enforce the
mechanical contracts, while a helper cannot establish source authenticity or
review classifications. A new serializer/CLI is not needed for this two-species
freeze. Explicit reviewed tables and existing Python data-layer APIs suffice.

M11.6b may begin after review of this specification. It must resolve the explicitly
unobserved facts: authoritative parent acquisition evidence, upstream checksum
entries, archive/plain payload hashes and full parser compatibility; then finalize
durable parent bytes/paths, complete per-contig reviews, construct/reinspect QC
resources, and issue real qualification records/catalog entries. These are
completion gates, not automatic choices. No final parent-manifest/QC/catalog
hash or production qualification is claimed in M11.6a. Failure to establish
authority or compatibility blocks dependent construction and requires review.

M11.6c requires the final parents and recorded deployment capacity, a durable
qualified executable, both separately built/verified indexes, immutable build
evidence, clean published lookup root and runtime handoff. QC catalog readiness
is required before declaring the combined M11.6 resource handoff complete.
Real-data acceptance and biological conclusions remain M11.7/M11.8.

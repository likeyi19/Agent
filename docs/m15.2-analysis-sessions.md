# M15.2 — Durable analysis sessions and revisions

Historical M15.2 acceptance record. [M15.3](m15.3-prior-output-binding.md) adds
explicit retained outputs and opt-in contextual planning on this foundation;
its current contract supersedes only the originating-run-only limitation below.

Implemented against Agent `6999f437b9ea30941430ddcc3c227bf6f372c852`.
This is application navigation metadata, not scientific authority. No Planner,
AgentRequest, AgentPlan, RunStore scientific schema, owner, registry, or EpiZoo
contract changes are introduced. Acceptance remains subject to project review;
no commit or push is part of this milestone.

## Application API

`ResearchAgentApplication.sessions` lazily exposes `AnalysisSessions`. Ordinary
`run(request)`, `resume(run_id)`, and `cancel(run_id)` neither require nor create
session state. There is no CLI conversation interface or LLM change.

```python
from agent.application import OutputSelection

sessions = app.sessions
sessions.create("analysis")
state = sessions.run(
    "analysis", "turn-1", request,
    outputs=(OutputSelection("qc", "qc_step", "manifest_path"),),
    expected_generation=0,
)
# Output names are explicit caller labels, not Planner context handles.
revision = state.active_revision_id

# After another successful turn, navigate explicitly with a new turn identity:
state = sessions.switch(
    "analysis", "back-to-first", revision,
    expected_generation=state.generation,
)
```

The named step and result key must actually exist in the accepted run. A locator
pins the whole accepted step, so it is not merely a mutable pathname. It is not
an executable reference and does not claim fresh artifact-content verification.
The source store is the application's existing trusted RunStore.

Additional explicit methods:

- `create(session_id)` / `load(session_id)` return frozen `AnalysisSession`.
- `start_turn(session_id, turn_id, request, outputs, expected_generation=...)`
  captures the active base and effective request digest before work.
- `link_run(session_id, turn_id)` associates the exact request-derived run ID;
  the run may already exist or may not yet have been created.
- `recover(session_id, turn_id)` reconciles persisted terminal run status and
  conditionally activates a recorded application completion. It never invokes
  runtime execution, owner verification, or presentation.
- `complete_presentation(session_id, turn_id)` explicitly composes an already
  terminal successful scientific run through existing application presentation,
  records completion, then conditionally activates. It cannot resume pending
  production. Existing presentation verification may perform owner reconstruction
  when compatible accepted authority is unavailable. This is intentionally distinct
  from storage-only session recovery.
- `record_no_run_turn(..., outcome=..., expected_generation=...)` records an
  explicit `clarification`, `failed`, or `cancelled` outcome without changing the
  active state. It does not interpret natural language or ask questions.

No public API accepts caller-asserted application success. Completion is recorded
privately only from the owning application's result, checked against the stored
scientific run. All APIs return structured metadata, not generated explanations.

## Exact persisted schema

`<workspace>/sessions/<sha256(session_id)>.json` contains:

```text
{
  format: "agent.analysis-session.v1",
  sha256: SHA256(canonical(record)),
  record: {
    session_id: string,
    schema_version: 1,
    active_revision_id: string | null,
    generation: nonnegative integer,
    revisions: [AnalysisRevision],
    turns: [SessionTurn],
    navigation: [Navigation]
  }
}

AnalysisRevision = {
  revision_id: string,
  parent_revision_id: string | null,
  turn_id: string,
  request_id: string,
  run_id: string,
  run_result_sha256: sha256,
  outputs: [OutputLocator]
}
OutputLocator = {
  name: string,
  run_id: string,
  step_id: string,
  output_key: string,
  accepted_step_sha256: sha256
}
SessionTurn = {
  turn_id: string,
  base_revision_id: string | null,
  base_generation: nonnegative integer,
  request_id: string | null,
  request_sha256: sha256 | null,
  run_id: string | null,
  status: string,
  selections: [{name: string, step_id: string, output_key: string}],
  revision_id: string | null,
  run_result_sha256: sha256 | null,
  completion_files: [{path: string, sha256: sha256}]
}
Navigation = {
  turn_id: string,
  from_revision_id: string | null,
  to_revision_id: string,
  generation: positive integer
}
```

Revision IDs are SHA-256 of canonical `{session_id, turn_id}`. The request digest
covers the unchanged effective AgentRequest after the application's ordinary
managed-output transformation. Completion file records pin presentation bytes
(evidence, visualization if present, report); they do not copy artifacts or
scientific authority. Run-result and accepted-step digests bind existing history.

All JSON shapes are closed. Duplicate keys/identities, invalid versions, malformed
history, broken parent/turn/output links, checksum mismatch and oversized records
fail closed. The engineering limit is 16 MiB per snapshot; reaching it does not
silently prune history. The workspace is trusted/local, not an authenticated or
hostile-filesystem service.

## State and durability

Typical scientific turn states are:

```text
started → linked → run_succeeded → ready → activated | stale
                  └→ failed | cancelled | planned
```

A normal uninterrupted application call can move directly from `linked` to
`ready`. `run_succeeded` means terminal scientific success without recorded
application completion; it may reflect interrupted or failed presentation.
Only `ready` can publish a revision. A stale completed revision is retained,
with its captured parent, but is not automatically activated.

The active pointer, immutable revision append, turn outcome, and navigation append
are one atomic session snapshot update. A per-session `flock` serializes short
metadata transactions; canonical JSON and SHA-256 detect corruption; temporary
files are fsynced, atomically replaced, and the directory fsynced. Revision and
navigation prefixes cannot be rewritten. Terminal turn outcomes cannot change.
Scientific RunStore files are never rewritten by session operations.

Every successful activation or explicit switch increments generation, including
an explicit switch to the same revision. Turn start and completion metadata updates
do not increment it. Activation compares both captured generation and base revision.
An A→B→A sequence therefore cannot admit a stale completion. Explicit switches with
stale generations fail. Repeating the same completed turn/navigation ID with the
same inputs is idempotent and never switches state again.

Parent history and previous-active history are separate: parent links represent
analysis ancestry, while ordered navigation records preserve the previously active
revision. No branch names, merging, event-sourcing engine, or transcript is added.

## Crash and failure boundaries

- Before/after linking but before run creation: no active change. A repeated linked
  submission never silently starts science. The caller can explicitly run the exact
  request through the existing one-shot API, then complete its linked turn.
- During a nonterminal run: session recovery reports existing linkage and never
  resumes scientific work. Ordinary explicit runtime/application resume retains its
  existing meaning.
- Scientific success before durable application completion: recovery records
  `run_succeeded`. Explicit `complete_presentation` handles the existing success,
  without another production invocation. Session recovery does not treat a report's
  mere presence as proof of application success.
- Durable `ready` before activation: a fresh process verifies the stored request/run
  and presentation-byte anchors and finishes activation with zero production and
  zero owner reconstruction.
- Activation committed but acknowledgement lost: repeat recovery returns the existing
  revision/outcome without duplicate history, even if navigation has since advanced.
- Failed/cancelled/planned work or failed presentation: prior active state remains.
- Generation lost during work: preserve the successful child revision as `stale`;
  do not overwrite newer navigation. It remains explicitly navigable.

Navigation validates historical run/result/step anchors using RunStore metadata.
It deliberately does not reread/reconstruct scientific outputs or claim they are
currently scientifically valid. Execution-time artifact validation belongs to M15.3.

## Deliberate M15.2 bounds relative to M15.1

Each revision's explicit output set is selected entirely from its originating run.
There is no implicit inheritance or union of old and new outputs. This prevents
M15.2 from silently carrying stale downstream results into new state. Multi-run
active sets require later reviewed binding/compatibility work; the locator itself
already carries run identity. No scientific lineage is reconstructed by this layer.

Storage recovery and unfinished presentation completion are separate APIs. This is
necessary to preserve both the existing application-success boundary and the strict
zero-owner-reconstruction guarantee for session navigation/recovery. Broad scientific
reverification is not hidden inside a state-management method.

## Validation

Focused tests use a synthetic registry tool and a synthetic presentation fixture;
no real scientific producer or LLM provider is invoked by the session suite. Tests
for navigation/recovery forbid runtime, executor, presentation and owner-context
verification calls. A subprocess verifies fresh-process activation and idempotence.
Coverage includes branch history, ABA races, simultaneous activation/navigation,
immutable revisions, failed/planned/cancelled work, presentation failure, existing
run attachment, corrupt/rehashed metadata, symlinks, failed publication, and lost
acknowledgement after commit.

Scoped regression: `tests/application`, `test_run_store.py`, `test_resume.py`, and
`test_cancellation.py`: **172 passed in 8.58 s**, including 35 session cases. This includes one-shot application,
CLI/workspace, legacy persistence and same-run lifecycle tests. No full scientific
acceptance suite was run.

## B. Architecture simplification review

There are **three new core application modules across M16.1/M16.2**:

| Module | Responsibility / review disposition |
| --- | --- |
| `dialogue_evidence.py` | Reads exact accepted persisted evidence, checks completion/source bindings, returns ephemeral bounded views. No new authority, owner reconstruction or report build. Keep. |
| `scientific_dialogue.py` | Captures/admits scientific references; supplies bounded evidence; validates structured generation. Keep one capability-agnostic path. |
| `dialogue_execution.py` | Admits explicit registered-tool commands, validates explicit output selections against the actual plan, links session turns and invokes existing Planner/Application. It performs substantive boundary validation, not just forwarding; keep separate. |

Existing `sessions.py`, `turns.py`, `turn_context.py`, `turn_decisions.py` and
interaction schemas continue to own the unified interface and M15 lifecycle.
The evidence facade is an API entry point, not another storage layer. No extra
module or state machine was added in this closeout.

Wire handles, immutable captured reference triples and returned evidence-source
locators are projections of the same revision/output identity for different
boundaries. Some anchors deliberately repeat the accepted-step digest so an
admitted reference can be checked against reloaded evidence. These are not
independent sources of truth; removing those checks merely to shorten records
would not simplify the trust boundary. No parallel focus store, copied generated
truth, second session or new authority exists.

Capability-aware evidence adapters remain (annotation group extraction and the
existing exact QC profile check); they expose reviewed scientific structure,
not capability-specific intent routing. No Groq model-name branch or semantic
workaround exists in generic application code. Distinct wire discriminators are
ordinary portable schema design, normalized to existing application decisions.

## C–D. Issue classification

**Permanent Agent/interface improvements:**

- Canonical subject IDs alone unnecessarily rejected an explicitly offered
  literal reference form for the same candidate.
- The generation protocol required the model to duplicate every reference in
  both a magic prose slot and a separate ID list. Those representations could
  disagree without changing the intended selected claim.
- Reviewed labels, Registry field descriptions and exact owner-profile scope
  metadata existed but were incompletely exposed to generation.

**Provider limitations, not reasons for semantic heuristics:**

- Misunderstanding explicit reviewed qualification/scope or adding unsupported
  conclusions despite the supplied contract.
- Awkward sentence joins, raw-field dumping and weak synthesis.
- Writing forbidden factual literals in text when structured references are
  available and the instruction explicitly requires them.

Not every old unit error can retrospectively be classified as provider-only:
some earlier context lacked reviewed meanings. Missing machine-readable units
remain unknown; this closeout does not fabricate them from implementation code.

## E–F. Subject reference contract

The existing bounded subject adapter supplies up to 32 canonical candidates.
Each candidate has one ID and up to four exact reference forms, each at most
128 characters. Forms include the canonical ID and bounded literal spans from
the current immutable user question: an immediately preceding word of at most
32 letters plus that exact ID. Thus `cluster 7`, `donor 7` or `sample 7` may be
offered when actually present; their prefixes are **not interpreted** as
scientific metadata. Existing group rows have no separate reviewed display-name
field, so user-quoted forms are explicitly reference spans, not invented owner
labels.

The LLM still decides whether the phrase is a subject reference and which result
it refers to. Deterministic resolution only compares its returned reference
against that result's offered candidate forms. Exactly one candidate must match.
Zero matches or collisions fail closed, including collisions with another
candidate's canonical ID. No case folding, numeric conversion, prefix stripping,
fuzzy matching, unbounded aliases or global registry. The provider reference
must also be grounded in the current utterance under the existing rule.

Only the canonical ID is admitted/persisted. The ephemeral reference forms are
reconstructed from accepted evidence and the same immutable question, not stored
as a second state. The redundant `subjects.ids` list was removed; canonical IDs
now appear once in the candidate collection. Existing `@focus`/`@other` and
predecessor validation remain unchanged. Unknown IDs now clarify at admission,
rather than waiting for generation to discover absent subject detail.

## G. Structured generation contract

Generation wire version 2 uses ordered paragraph parts:

```json
{
  "support": "supported",
  "paragraphs": [{"parts": [
    {"kind": "text", "text": "The accepted assignment is"},
    {"kind": "claim", "id": "c0"},
    {"kind": "meaning", "id": "m0"}
  ]}]
}
```

All objects are closed. Reference IDs are bounded enums; union kinds are
distinct. The model selects an ID once. The Agent inserts the complete exact
target/subject/predicate/value record or reviewed meaning. It never accepts
replacement subject/value/predicate members. Unknown handles, additional
members, absent comparison operands and unbound factual literals fail closed.
The existing literal checks remain defense in depth, not semantic entailment.

Removed: magic-slot parsing, the duplicate `claims`/`meanings` lists in provider
paragraphs, and consistency logic between those lists and prose placeholders.
No legacy generation decoder or fallback chain was retained. Scripted fixtures
were updated to the new ephemeral wire contract. Durable session records never
contained generated prose, so no migration or new persisted schema is needed.
Returned `ScientificClaim`/`ScientificResponse` application types remain.

## H. Reviewed semantic transport

Existing report `_FIELD_LABELS` are exposed only for applicable tool report
fields, verbatim. Existing `ResultContract.planning_fields` descriptions are
also exposed verbatim with their source identified. Rendering uses the reviewed
label where available; exact original field identity and JSON pointer remain
in the returned claim.

Examples include `QC resource qualification`, `Barcodes with defined TSS
enrichment`, and `Primary nuclear QC fragment records`. The existing exact
method/profile match additionally exposes the frozen owner's `QCScientificProfile`
verbatim: count scopes, endpoint support, enrichment ratio, length/histogram
scope, nucleosome ratio and undefined-background behavior. A different accepted
profile does not receive this metadata. No new QC interpretation prose was added.

No generic unit map or nested-field meaning is invented. Unspecified metadata
stays absent. Container descriptions are not reassigned to arbitrary children.
The existing reviewed scope notes and profile-gated TSS explanation remain;
this is read-only metadata transport, not scientific verification or inference.

## I–J. Responsibilities

The same candidate resolver, reference-part renderer and semantic metadata
projection serve all capabilities. Tests include QC, selection, annotation,
matrix, adaptation and embedding descriptions. New tools need no keyword route.

The LLM owns language, intent, reference interpretation and explanation. The
Agent owns offered identities, exact canonicalization, evidence binding,
validation and routing. Owners retain computation and scientific truth. A
stronger provider implementing the existing `complete` abstraction can replace
the current model without architectural change.

## L–M. Minimal live compatibility check

Exactly **two API calls**, Groq `openai/gpt-oss-120b`, established Agent Conda
configuration, zero SDK retries, no fallback. One ordinary `respond` turn used
the preserved accepted real annotation run and an isolated session copy:

> What does the accepted annotation result show for cluster 7?

Call 1 returned a valid `answer_scientific` decision targeting output `r0`,
canonical subject `7`. Admission selected the exact accepted annotation result.
Call 2 accepted the new strict generation schema and returned three claim
references (`c0`, `c1`, `c2`) and reviewed meaning `m0`. All three selected
references were independently checked against exact pinned evidence pointers;
their subject was `7` and their fields were `n_cells`, `primary_annotation`
and `status`.

However, the text part also said:

> The accepted annotation result for cluster 7 includes the following details:

That raw numeral violates the explicit text-part contract. The unchanged
factual-literal validator rejected the **whole answer**. The user-facing result
was `unavailable`; no accepted `ScientificResponse` was returned. This is not a
successful end-to-end live answer and is not counted as one. Schema, target and
reference compatibility were demonstrated; full response admission was not.

Classification: **PROVIDER_LANGUAGE_QUALITY_LIMITATION — text-contract
noncompliance despite explicit structured references**. No unknown claim, wrong
subject binding, substituted scientific value or new scientific computation was
accepted. The offered IDs were valid; no repair, retry, model switch, subject
prefix exception or further live call was made. No HTTP 429/outage occurred.
Both canonical-ID and literal-form choices are covered deterministically; the
live model chose the canonical ID, not the alternative reference form.

The final owner-profile transport and redundant-ID-list removal occurred after
this annotation smoke. They were tested locally; no additional network call was
made. Neither changed the tested generation schema or canonical subject identity.

## P–Q. Risks and recommendation

Structured claims are authoritative only through accepted evidence; explanatory
prose still lacks complete deterministic entailment checking. Correct context
cannot guarantee intelligent explanations. Some fields lack structured reviewed
unit metadata, and literal validation can reject harmless repeated facts. These
are explicit interface/coverage limits, not a new scientific authority or a need
for deterministic natural-language heuristics. The latest failure does not
justify adapting the architecture to the current model's wording.

Tier 1 deterministic correctness is accepted. Tier 2 demonstrated schema and
reference integration but did not produce an admissible full live answer in
this two-call check. Tier 3 language and compliance limitations remain recorded;
the current provider's end-user quality is **not** qualified. Close the bounded
M16.2 architecture scope under the requested primary deterministic gate; keep
provider-quality qualification separate.

Explicit answers:

1. New scientific authority: **No**.
2. New session architecture: **No**.
3. Capability-specific dialogue routing: **No**; reviewed evidence adapters are
   not intent routers.
4. Groq-specific semantic workaround in generic code: **No**.
5. Safe semantic-reference canonicalization: **Yes, only within uniquely matching
   offered candidates; no open-ended guessing**.
6. Deterministic factual claim binding: **Yes**.
7. Meaning/unit/qualification provenance: **Existing reviewed contracts, report
   metadata and identity-matched owner profile only; missing metadata is not invented**.
8. Stronger future LLM substitution without redesign: **Yes**.
9. Further tuning to this model's prose primarily optimizes the provider: **Yes,
   absent a newly demonstrated independent interface defect**.
10. Architecture remains minimal and conceptually clear: **Yes**; three justified
    modules on the existing session/evidence/provider path, no parallel engine.

This recommendation does not start M16.3. Nothing is committed or pushed.

**M16.2 architecture accepted and closed; remaining live-language issues are provider-quality limitations. Proceed to M16.3.**

# M17.1 — Read-only capability-grounded scientific guidance

M16 remains closed at M16.3. M17.1 adds conditional scientific guidance to the
existing `sessions.respond` interface. It does not implement candidate execution,
new scientific tools, new scientific facts, or a second Planner.

## Interface and responsibility

The existing interpreter can return `answer_guidance` with zero to four exact
`ScientificTarget` references, or an exact predecessor candidate reference.
`Answer(intent='guidance', guidance=GuidanceQuestion(...))` is admitted through
normal interaction capture. The user's objective remains the original interaction
utterance. Guidance requires an existing accepted analysis revision, like the
current M15/M16 high-level interaction interface.

The generation provider uses the existing `complete(prompt, response_schema)`
boundary. It selects one to four distinct registered tools as advisory candidates
and supplies three explanation paragraphs: question/rationale, assumptions and
limitations. Separate candidates express alternatives; one candidate per tool is
the current bound. No workflow, executable arguments or DAG is emitted.

`TurnOutcome.guidance` contains immutable `GuidanceResponse` / `GuidanceCandidate`
views. Each candidate carries an exact reference, Agent-produced readiness facts,
and the existing `ScientificResponse` claim/explanation representation. Its
`support` describes the evidence-backed explanation, not proof that a recommendation
is scientifically optimal or executable. Generated reasoning is explicitly
conditional and is never scientific authority.

Representative scripted interactions:

- “What should I analyze next?” — bounded registered candidates with conditional
  rationale and explicitly incomplete readiness.
- “Why does cluster 3 differ? What could I analyze?” — the exact admitted annotation
  subject and accepted facts accompany the objective; no cluster correspondence,
  marker discovery or new biological conclusion is inferred.
- “Why would the first option help?” — the captured candidate and original objective
  are reused; current accepted evidence is reloaded and explanation regenerated.
- “Option 1 sounds right. Do that.” — unsupported clarification; no Planner or
  scientific work. Explicit candidate execution is deferred to M17.2.

These illustrate scripted interface acceptance, not live language-quality claims.

## Architecture reuse

`scientific_guidance.py` owns only bounded advisory composition, candidate-reference
admission/completion and Registry context. This separates advisory semantics from
M16 compatible comparison while sharing its actual evidence/context/renderer code.

Existing `scientific_dialogue.capture` selects a unique scientific/guidance discussion
leaf using the existing predecessor and concurrency rules. `ScientificTarget`
resolution supplies exact revision, output and subject bindings. Broad guidance
can explicitly select multiple current outputs without requiring each output name
in the utterance; historical and within-result subject admission remain exact.
A multi-output guidance set has no implicit single subject. Follow-up `@focus`
therefore clarifies unless a unique target exists.

The actual `build_semantic_planning_catalog` function supplies all capability
purpose, semantic ports, source modes, constraints, defaults and choices. There
is no copied catalog, prerequisite resolver, compatibility algorithm or workflow
traversal. The Registry remains 23, with no description or scientific contract edits.

## Readiness and advisability

M17.1 binds no execution inputs, including inputs passed for the separate execute
route. The catalog is projected over an explicitly empty advisory request. It can
state:

- the candidate is registered;
- selected exact accepted evidence is present (handles refer to the supplied set);
- required ports have no supplied **request** source in this advisory context;
- which required parameters are marked scientific in the existing metadata;
- existing request-source choice facts and declared constraints.

Absence of a request source is not absence of all possible inputs: ports may also
accept upstream outputs. Selected evidence is not asserted to be an executable
input. `readiness='not_fully_checked'` is always explicit. Historical bindings,
source/consumer compatibility, runtime dependencies, design suitability and plan
preflight are not assessed here. Readable M16 evidence need not qualify for M15.3
historical execution reuse. Guidance does not invoke those execution checks or
reconstruct accepted scientific results.

All readiness fields are attached by the Agent, never supplied by the model.
Unknown fields such as `runnable_now`, fabricated bindings or compatibility claims
are rejected. Scientific usefulness remains conditional LLM reasoning; technical
facts never select a recommended capability. No deterministic biological ordering,
recommendation score or `after X -> recommend Y` rule is present.

## Bounded heterogeneous evidence and grounding

Guidance reuses M16 `sessions.evidence`, reviewed sidecar adapters, exact claim
sources and rendering. Up to four selected heterogeneous targets share the existing
64-claim / 32-KiB evidence budget, with a per-source allocation and room reserved
for available reviewed detail. Omitted fields/detail are explicit. Unselected
output counts and general coverage limitations are visible. Catalog plus evidence
context is capped at 128 KiB; response parsing retains M16's 16-KiB bound.

Co-presence is not comparison. No M16 compatible-comparison pairs are constructed
for guidance, and M16.3 comparison admission is unchanged. Common revision, labels
or tool types do not prove common populations, biological equivalence or subject
correspondence. The first within-result subject adapter remains annotation groups;
unsupported subjects fail closed rather than being inferred from arbitrary results.

Structured accepted facts use offered claim IDs and retain revision, output locator,
evidence digest and pointer attribution; detailed claims retain published artifact
identity. Capability IDs are exact Registry members. Readiness cannot be model
replaced. The shared renderer rejects unknown references, raw numeric literals and
unbound accepted categorical values. Unknown tools, malformed records, duplicate
candidates, stale context or evidence mutation yield no guidance response.

Evidence and catalog are reloaded after generation. Changed consumed context fails
closed. Navigation does not rebase a captured answer: it is labeled historical.
No owner production, reconstruction, Planner, preflight or presentation is invoked.

As in M16, these checks do **not** prove arbitrary prose entailment. Conditional
scientific reasoning, qualitative overclaims and semantic appropriateness of advice
remain model-quality concerns. Provider instructions separate reasoning from facts;
structured grounding and explicit non-authority do not establish universally
hallucination-free prose.

## Candidate identity and persistence

`Interaction.guidance_candidates` is an optional completion-only reference field in
the existing session record. This field is needed because admitted intent is
immutable and generated candidates are not known at admission. It is written once
with successful completion, validated on load, and immutable thereafter. Existing
records decode with an absent field; non-guidance serialization omits it.

A candidate identity hashes session, originating turn, objective turn, captured
revision, registered tool and exact evidence-context targets. The guidance admitted
record pins the Registry catalog digest. Candidate references are canonically
sorted by capability name; displayed option numbers are presentation references,
not recommendation ranks. Replays cannot change the candidate set or reorder it
based on regenerated prose. Rationale follow-ups preserve the originating candidate
identity, objective and context and reject changed revisions/catalogs.

Only references are retained. No rationale, claim values, recommendation ranking,
readiness conclusions, generated answer, new evidence projection or advice authority
is persisted. Concurrent completion cannot replace a winning candidate reference
set; failed or stale attempts cannot overwrite successful completion. Discussion
branches use existing predecessor IDs, never a separate guidance session/store.

## Provider and execution boundaries

No provider code changes. The prior DashScope DeepSeek Responses qualification
remains independent of M17.1. No live calls are part of this implementation.

Scientific owners, authority schemas, Registry science, executable Planner,
compiler, preflight and EpiZoo are unchanged. Candidate-to-Planner handoff,
automatic prerequisite completion, autonomous execution, a synthesis engine,
biological workflow rules and provider-specific prompt/repair logic remain out of
scope. Candidate references provide an appropriate boundary for later explicit
M17.2 selection without implementing that handoff now.

## Architecture and scope

```text
Browser HTML/CSS/JavaScript → same-origin FastAPI → InteractiveAgentApplication
→ existing Session/dialogue/guidance/application → Planner/compiler/preflight
→ runtime/verification/evidence/persisted presentation
```

Every HTTP domain operation calls the interactive facade. Static delivery reads
only the bundled frontend assets. No route accesses RunStore, SessionStore,
Planner, scientific tools, authority or user-selected filesystem paths. Existing
client projections are serialized with their `to_dict()` methods; HTTP models
validate only the small incoming transport bodies.

The sole application addition is read-only `validate_submission`, sharing the
existing submit admission checks and returning a normalized fingerprint for
local in-flight coalescing. It invokes no provider, writes no records and reserves
no identity. `submit_turn` retains its existing processing lease, exact immutable
submission, generation checks and persisted presentation semantics. Predecessor
validation also remains repeated under that lease. Scientific contracts, Registry,
Planner semantics, evidence/authority ownership and M17.2 are unchanged.

## Operator configuration and launch

Use the existing Agent Python environment, from the repository root:

```bash
python -m pip install -r requirements-web.txt
PYTHONPATH=src python -m agent.web --config /absolute/operator-web.json \
  --host 127.0.0.1 --port 8000 --max-workers 2
```

Host defaults to `127.0.0.1`, port to `8000`, and local submission workers to
`2` (allowed range 1–8). One Uvicorn server process serves both API and assets.
For a remote lab host, SSH forwarding lets a local browser reach the loopback
server: `ssh -L 8000:127.0.0.1:8000 lab-host`, then open
`http://127.0.0.1:8000/`. Choosing another bind address is explicit operator work.
Authentication, public hosting and multi-host execution are outside this stage.

Example operator JSON; replace the model ID with an explicitly admitted model:

`WebConfiguration` and `build_interactive_application` form the composition
point. Profiles are existing `PlanningModelProfile` values, with the existing
immutable `PlanningModelFactoryRegistry`. Built-in providers remain OpenAI,
Gemini and Groq; their existing SDK/environment requirements apply. Credentials
are read server-side from `OPENAI_API_KEY`, `GEMINI_API_KEY` or `GROQ_API_KEY`.
Startup, health and model-choice reads do not instantiate provider clients.
No live-provider language quality is qualified here. Python composition can
inject the existing registry/factory/executor for deterministic testing.

Strict JSON configuration rejects unknown/duplicate fields and non-finite
numbers, is bounded to one MiB, and allows at most 64 profiles/input sets.
Relative workspace locations resolve beside the configuration file, preserving
the application's existing symlink rejection. Scientific input paths remain
exactly operator-declared. Input sets are immutable ordinary M18.2 structured
inputs: browser requests supply only an offered input-set ID. The server forwards
the corresponding mapping to the facade, without scientific inference or input
completion. Null/absent choice forwards empty inputs. Outputs, authority and
internal bindings remain application-owned. Changing the resolved scientific
input mapping changes submission identity; retries retain the exact original
inputs and profile configuration. Input-set IDs and labels are display/configuration
selection only, not a second scientific identity.

Dependencies follow the existing requirements-file convention. Optional runtime
dependencies are FastAPI and Uvicorn; HTTPX is the focused test dependency.
FastAPI's declared minimum requires Pydantic 2, used for strict transport-only
validation ([FastAPI release notes](https://fastapi.tiangolo.com/release-notes/)).
The empty `pyproject.toml` and existing CLI remain unchanged.

## HTTP surface

All JSON operations are under `/api/v1`. Responses contain existing client-safe
views or the small shapes below, never internal storage serialization.

| Method/path | Request and response |
| --- | --- |
| `GET /health` | `{"status":"ok"}`; no provider/scientific readiness checks |
| `GET /models` | `{"choices":[ModelChoice...]}` from the facade |
| `GET /input-sets` | Offered input-set IDs and display labels only |
| `POST /sessions` | `{}` or `{"session_id":"..."}`; `201 SessionView` |
| `GET /sessions/{session_id}` | Bounded persisted `SessionView` |
| `POST /sessions/{session_id}/turns` | Submission below; `202 {session_id,turn_id}` |
| `GET /sessions/{session_id}/turns/{turn_id}` | Existing `TurnView` |
| `GET /sessions/{session_id}/turns/{turn_id}/status` | Same coarse checkpoint projection |
| `POST /sessions/{session_id}/turns/{turn_id}/cancel` | Existing cooperative cancellation, then `TurnView` |

```json
{
  "turn_id": "stable-client-generated-id",
  "expected_generation": 0,
  "utterance": "Inspect the supplied matrix.",
  "profile_id": "lab-model",
  "input_set_id": "tiny"
}
```

`profile_id`, `input_set_id` and the existing `predecessor_turn_id` reference are
optional. Unknown/extra browser fields are rejected. HTTP-created session/turn
IDs exclude slash/backslash and exact dot segments so they remain addressable as URL segments; existing
Python session IDs retain their original contract. Session histories use the
facade's default bound of 100 entries and expose truncation. No enumeration,
artifact delivery, raw evidence or automatic recovery endpoint is introduced.

## Submission, polling and restart

Submission validates through the facade before invoking a bounded local
`ThreadPoolExecutor`. It returns identity without awaiting scientific completion.
Saturated workers return `503 WEB_WORKERS_BUSY`, without queueing or provider
invocation; the same payload/ID can be retried explicitly. Browser disconnects
do not cancel or redefine application execution. Graceful shutdown drains calls.
No extra durable job database, workflow queue, distributed scheduler or mutable
global model selection exists.

At most 128 process-local receipts cover in-flight identity, the short interval
before Agent captures a turn, and failures before capture. They are transport
coordination only. Once captured, status reads prefer the facade's persisted
projection. New-server reads/retries never call the interpreter, Planner or tools
for captured work. Restart loses transient receipts but preserves existing Agent
state; it never automatically resubmits uncertain work. A `202` receipt alone
does not guarantee durable capture. A pre-capture failure has a safe transient
failed view, but no fabricated durable conversation entry.

Polling normally runs every two seconds. Scientific terminal checkpoints can
precede the exact presentation write; the browser continues at five seconds
until the stored display is available. Ordinary completed replies, interrupted
checkpoints, unavailable records and pre-capture failures stop polling.
No percentage, ETA, heartbeat or worker-liveness claims are added. Steps retain
the application's existing checkpoint statuses and attempt counts.

Unfinished interpretation/planning after a process crash is not replayed. For
scientific reconciliation or unfinished presentation, operators explicitly use
the existing Python `interactive.recover_turn(session_id, turn_id,
complete_presentation=True)` when applicable; scientific runtime resume remains
the existing explicit planner-free application operation. Polling/reopening
performs neither recovery nor response regeneration. Reporting-stage cancellation
and a recovery UI remain deferred.

## Browser behavior and safe failures

The centered static page has session controls, admitted model/input selectors,
conversation and a composer/status area. New sessions are empty durable Agent
sessions. Known-ID reopen and refresh reconstruct Session, generation, active
revision and exact persisted user/assistant text. Assistant answers,
clarifications, results and safe errors have distinct display labels. Text is
rendered through `textContent`, never HTML interpretation or evidence inference.

The selector uses exact offered profile IDs and friendly labels/default markers.
Changing it affects only the next submission and creates no scientific revision.
Each turn keeps M18.2's separate configured client/application bundle.
The cancel button appears for persisted planning/validated/running checkpoints
with a scientific run ID and invokes the
existing cooperative cancel operation; a request is followed by polling, not an
optimistic fabricated cancellation result.

Browser storage contains only session ID, selected profile ID, polled turn ID and
unsent draft. The current exact retry payload is held in memory; refresh never
resubmits it. Agent owns Session/Revision/generation/Interaction/submission/run,
status, presentation, guidance, evidence and authority. Reopening uses Agent
values, not cached browser generation or reconstructed LLM conversation.

Expected boundary failures preserve `ClientError` codes/messages in
`{"error":{"code":"...","message":"..."}}`. Unknown sessions/references use
404; stale/conflicting submissions use 409; unknown profiles/inputs use 400;
invalid transport shapes use 422; unexpected application failures use 500.
Normal API responses never include exception prose or stack traces. Server logs
retain debugging traces. JSON mutations reject foreign Origin headers, no CORS
is enabled, and the page loads only same-origin assets. Browser-authored provider
settings, paths, plans, bindings and authority are rejected.

M18.4 retains guidance cards/selection UI, rollback/branch/revision navigation,
evidence/provenance panels, reports, figures, downloads and richer scientific
intake/resource UX. Existing guidance prose may display normally, with no bypass
of M17.2. No generic filesystem browser or arbitrary path textbox exists.
Advanced recovery UI, session enumeration, multi-process/distributed hosting,
authentication and Internet deployment are not supplied. Separator-containing
or dot-segment historical IDs remain Python-only. Full milestone regression/closeout is M18.5.

M18.3 introduces no architecture deviation beyond the documented read-only
facade operation and optional thin transport. Commit/push require separate user
review and authorization.

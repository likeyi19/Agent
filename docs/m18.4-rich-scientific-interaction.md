## Application boundary and scientific ownership

```text
Static browser → same-origin FastAPI → InteractiveAgentApplication
→ existing Session/dialogue/guidance/evidence owners
→ existing Planner/compiler/preflight/runtime/authority
```

No new scientific tool, Registry entry, numerical method, species contract,
authority format, binding logic or workflow inference is introduced. Scientific
owners, evidence owners, M17.2 selection and existing model construction remain
unchanged. No route accesses stores, paths, tools or providers directly.

The facade adds `revision`, `activate_revision`, `evidence` and
`artifact_content`. Rich `RevisionView` extends the existing projection rather
than creating a second scientific revision model. Session reopening remains
bounded and lightweight; detailed views are fetched on demand. New
`EvidenceView` preserves the existing owner's availability, coverage, facts,
detail, limitations and source attribution. `ArtifactContent` supplies bounded
bytes with server-controlled type/name and distinct source/content digests.

New turn views expose the captured base revision. New scientific display records
retain safe target references from exact existing scientific admission, with
claim-source references as the fallback for standalone display conversion; this
distinguishes a question's captured base from an explicitly historical/comparison
target even when a response uses no claim slots. New guidance display records
retain the owner's existing readiness and
captured-base metadata. No scientific claim-value table or executable authority
is stored in presentation. Legacy shapes stay readable and historical wording
and display records are never regenerated or rewritten.

## Browser scientific state, navigation and continuation

Conversation and scientific state occupy separate panels. The scientific panel
shows active/historical revision, parent, associated turn/run, original base
generation, current session generation, actual checkpoints, retained output names,
stored result display, artifact inventory and evidence choices. Conversation
associates captured base, scientific targets and created results separately.

Selecting a revision in history only browses it. **Switch to this revision**
calls the existing `sessions.switch` through the facade, using a unique navigation
turn ID and the browser's observed generation. Stale state, conflicting turn IDs,
unknown revisions and corrupt accepted anchors fail closed. Exact navigation
retries remain idempotent. Switching does not invoke a provider, scientific tool
or owner reconstruction and does not modify historical revisions.

**Continue from here** confirms activation of the chosen revision, then focuses
the ordinary composer. It may prefill `Continue from this result.`; it does not
submit or fabricate a plan/binding. The next natural-language request uses the
existing semantic interpreter and active Session context. A new execution creates
a child of that captured revision. Returning to an earlier revision and executing
again can create a sibling of an existing child: this is branching, with no
separate branch object.

Metadata-only navigation and historical non-conversation runs do not become chat
messages or pending conversational work. Their scientific revisions remain
visible; missing stored historical result display is explicit. This avoids
blocking the composer on a completed legacy run without a captured Interaction.

## Evidence, provenance and details

Opening evidence calls only `sessions.evidence` through the facade. The existing
owner validates accepted metadata and pinned evidence bytes; it never reconstructs
science, invokes standalone upstream verification or regenerates presentation.
The panel distinguishes evidence availability, coverage, bounded facts, accepted
verification checks, source run/step/output anchors, lineage, provenance and
limitations. Evidence remains distinct from conversation, guidance and reports.

Path/private-configuration-bearing whole values become explicit omitted facts
with `client_safe_content_omitted`, retaining pointers/digests where supplied.
Scientific values are not redacted, aligned or silently rewritten. This safe
projection is not scientific authority or a fresh validity claim. Unavailable or
unsupported evidence stays explicit, without a scientific fallback.

Only existing reviewed detail contracts are offered: QC `length_histogram` and
annotation `annotation_rationale`. The owner enforces section/subject/candidate
compatibility, digest-bound published files and owner-order limits (1–32 records).
Annotation subjects and optional exact candidates use those existing semantics;
the browser offers section, subject and record limit. Unknown sections or
unsupported subjects return explicit unsupported/unavailable views. No universal
artifact interpreter, OCR, biological ranking or scientific reconstruction exists.

## Reports, figures and downloads

Clients submit only application-issued handles scoped to Session/revision. The
facade checks accepted revision/run anchors, managed presentation ownership,
regular non-symlink files, pinned source digests and bounded reads. Inventory and
resolution do not repair missing directories. Wrong Session/revision, unknown,
tampered, corrupt or unsupported artifacts fail closed.

PNG delivery returns exact accepted bytes, with a 16 MiB bound, 40-million-pixel
cap, closed PNG validation and accepted plotting metadata. No image transformation
or new visualization algorithm is introduced. MIME and fixed `agent-figure-...png`
download names are application-controlled; the browser renders only supported PNG.

Original Markdown reports can contain server paths. Their bytes are validated
against the accepted digest but withheld. The downloadable/readable **client-safe
report projection** presents existing accepted revision-output evidence and its
limitations, with a one-MiB bound. It is explicitly different from the original
Markdown and is not a new scientific summary or authority. Source and delivery
digests remain separate; there is no regex redaction, arbitrary report parsing or
scientific report regeneration. Reports display as plain text, never HTML.
H5ADs, checkpoints, raw manifests and arbitrary file types are not delivered.

## Guidance and model selection

Each persisted guidance candidate is a card with stable identity/original ordinal,
capability, rationale, support, limitations, captured revision and stored technical
readiness where available. Missing legacy readiness is explicit. Capability
registration and `not_fully_checked` readiness do not establish execution authority.

**Continue with this** visibly starts a new ordinary turn containing
`Run option N.` and `predecessor_turn_id` from the persisted origin. It uses the
selected offered model and optional operator input set. There is no candidate
execution endpoint or candidate-to-tool shortcut:

```text
Click → ordinary turn submission → semantic interpretation → ExecuteCandidate
→ guidance_selection.admit → exact captured candidate/context/subject checks
→ validated PriorOutputRef → AgentRequest → existing scoped Planner
→ actual-plan output selection → compiler/preflight → runtime
```

Stale candidates clarify without planning/science. Returning to the exact captured
revision can restore applicability only through the existing fresh checks.
Model selection remains a next-turn preference; changing the dropdown does not
alter generation, revisions, accepted results, authority or historical replies.
Credentials/profiles/factories stay server-side under the M18.3 configuration.

## HTTP surface and durability

The existing M18.3 API, bounded local workers, cancellation, exact submission
idempotency, same-origin policy and safe errors are retained. Rich additions:

| Method under `/api/v1/sessions/{session_id}` | Operation |
| --- | --- |
| `GET /revisions/{revision_id}` | Rich existing revision projection |
| `POST /activate` | `{turn_id, revision_id, expected_generation}` → confirmed SessionView |
| `GET /revisions/{revision_id}/evidence` | Required `output_name`; optional repeated `fields`, `detail_section`, `subject`, `limit`, `candidate` |
| `GET /revisions/{revision_id}/artifacts` | Accepted handle inventory |
| `GET /revisions/{revision_id}/artifacts/{handle}` | Supported bytes; `download=true` selects attachment disposition |

Artifact headers are `X-Artifact-Source-SHA256`, `X-Artifact-Content-SHA256` and
`X-Artifact-Presentation` (`accepted_png` or `client_safe_report_projection`).
Names/content types come from the facade. JSON errors retain safe application
codes; artifact/reference failures use 404 and navigation conflicts use 409.
Strict transport bodies reject authority, plans, paths and unknown mutation fields.

Browser storage still holds only session/profile/polled-turn IDs and draft.
Viewing state is ephemeral. Session/Revision/generation/Interaction/submission/run,
presentation, candidate identities, evidence and authority remain Agent-owned.
Refresh/reopening reconstructs them from accepted projections, without replaying
work or regenerating wording. Fresh-server reads require no provider client.
Uncertain incomplete interpretation/planning is never automatically replayed;
explicit scientific recovery remains the existing Python/application operation.
Cooperative cancellation retains cancelled/interrupted distinctions unchanged.

Launch and operator configuration are unchanged from
[M18.3](m18.3-basic-web-application.md). No new dependencies, frontend framework,
Node tooling, authentication platform or distributed worker guarantees are added.
